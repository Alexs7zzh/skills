# Judged proposals

Read when the user says `judged` or `with a judge`, or a workflow you are running names this file. Read it before investigating so the investigator and judge use the same standard. This loop adds no ledger, runtime or coordinator; it does not replace obligations of an explicitly selected joint route. SKILL.md's Read for the work still applies to the investigator.

## One pause, then the work

Every cluster ends in a proposal with a recommendation, whether or not you could fix it now. A judge checks the proposal, a fresh writer turns the accepted proposal into the owner's hand-off under [handoff.md](./handoff.md), the batch lists every hand-off, and the user decides at that one pause. Ordinary implementation waits for that decision; when the user approves a fix or an investigation, do it under the run's authority with the ordinary change review. Filing an issue records the proposal; it does not handle the incident. When the user asks to file, publish under handoff.md, Publishing as an issue or comment.

Judge acceptance assesses a next action. It grants no authority to implement, publish issues, close incidents or expand scope. Follow the user's requested stopping point and the project's approval boundaries.

Implementation of an approved proposal starts by checking each fact in its Known against the current code. A fact that no longer holds returns the proposal to its investigator before any edit; this narrow check is cheap and catches both drift and a shallow claim.

A candidate experiment before the pause is allowed only when it is the cheapest way to prove a mechanism. Keep it out of the checkout and report it in Known as evidence.

Recommend the work you would do if the choice were yours. Deferral is not the safe answer: an unneeded issue costs the user a decision and delays a fix.

## The proposal

Apply The judge's standard during investigation, not only when writing the proposal. Write a compact decision explanation before the technical evidence. First explain the normal operation and intended handling of this situation, then what currently differs and why it needs attention. Name what failed and what still works; a rejected optional operation and an unusable product are different outcomes. For each separately approvable response, explain what it changes and why that helps. Distinguish a cause fix, mitigation, evidence improvement, logging change and retaining correct behavior. A list of engineering tasks does not supply this explanation.

Define a term when its meaning determines the decision. Spell out essential acronyms. Introduce file names, flags, stage inventories and incident counts after the reader understands the situation and response. Use the project's issue format when it defines one; every slot below still appears under some heading.

- **What happened.** The ordinary situation, its intended outcome and the observed difference, in language the owner can follow without subsystem knowledge. Say whether handling is defective, expected or still unclassified, and why the proposed attention is worthwhile. Include symptom, user consequence, meaningful secondary concerns, reach with its window and counting limits.
- **Known.** Checked facts and their sources, separated from hypotheses. Name the files read and the changeset. Give a design verdict for each stage on the traced path that the project owns: it handles the observed state and every value or event its inputs can deliver, or it does not and how. A stage shown unable to handle the observed state is a checked mechanism and supports fix now; see The judge on unattributed incidents.
- **Assessment.** Address the six numbered questions under The judge, Outcome and actions, with checked evidence or an explicit unknown. Answers may share prose or reference Known; an inapplicable question needs only a brief reason. Keep these answers here, not as a questionnaire in What happened.
- **Unknown.** The questions that affect the next decision, what has been tried, and what blocks answering them now from the code and evidence you had. "Not enough evidence" alone is not a blocker, and a limit of the telemetry is a blocker only when the code at that changeset cannot answer the question either.
- **What does not fit.** Observations that weaken this explanation or could change the recommendation, each with what it would change, or `none`. Never omit one because the judge could not evaluate it.
- **Recommendation.** Select every supported response from the assessment; one reporting change must not stand in for otherwise required design review, recovery or feedback work. For each separately approvable response, recommend fix now, investigate now, issue, existing issue applies, update or reopen an existing issue, no action, or wait. State its committed operations and what they establish or improve. Fix now requires that Known proves the mechanism and the change follows from it. Name the strongest alternative considered and why it lost; a recommendation with no rejected alternative has not looked for one. Investigate now names the bounded investigation or reproduction and the decision its result changes. A committed check must be able to fail: if the proposal already states the result the check will return, it establishes nothing and is not an operation. For a once-observed anomaly on a path every session exercises, attribute first to a local stall or crash on that client and ask the recovery question (does the held state converge once the client resumes, and what would show it) before proposing to reproduce the path's normal behavior; the project's runtime assumptions may already classify the stall as expected. Before recommending reproduction or new capture, say which values or callbacks the owned code can be fed in a spec to drive the hypothesized branch; a spec that drives it is a committed operation and needs no hardware or field recurrence. For new capture, name the decision its possible results change. For no action or waiting, give the evidence or cost reason useful work should stop now and what would reopen it. Name the signal that would show the reopen condition and where it is observed: a forwarded telemetry line and its query, a server metric, or a user report. A local-only log or a value the code computes but never ships does not count. If nothing observable shows the condition, commit the smallest change that would, or state that the condition is accepted as unobservable and why.
- **Scope and risk.** Boundaries and owners touched, relevant support or owner constraints, tradeoffs, the main regression or validation risk, and how the result will be checked.

Write the recommendation after every owned stage on the path has its verdict, not when one explanation satisfies you. The required technical coverage stays in this proposal. The owner's hand-off is a separate text that a fresh writer produces from the accepted proposal under [handoff.md](./handoff.md); the investigator does not write it, and answers the writer's questions about an unclear or contradictory claim. Keep the investigation narrative, evidence dumps, earlier revisions and verdicts in your note. Put unresolved or rebutted objections in a separate dispute appendix for the batch list, never in a judge's or writer's packet.

## Dispatch the judge

Start a fresh agent for each proposal revision. Give it only The judge section below, the current proposal, and the applicable owner rulings, taken from the documents that own the affected feature and from the user's decisions at earlier pauses. Do not include prior verdicts, the dispute appendix, code, raw reports or your note. Deliver the packet inline or as one file whose length you state, so the judge can tell that it received all of it. Wait for its verdict before continuing that cluster. Use agent-messaging when available.

After Accept, dispatch the writer, then the writing judge, each a fresh agent with the packet handoff.md names. A writing push-back returns to the writer; a contradiction the writer finds returns to the investigator, and a changed claim is a new proposal revision for a new technical judge.

Keep review status outside the candidate text. Each status is Pending until you have read the returned verdict for that exact revision. In the batch list, show the technical verdict and the writing verdict separately, each derived from its recorded verdict with a link; a planned review or another revision's acceptance supplies neither. Updating a status after the result does not require judging again. Record the exact packet and verdict with the revision in your note, then close the disposable session.

## The judge

Decide whether this proposal gives the owner useful work toward the required product outcome, or a well-supported reason not to act now. You judge the next work package, not a final fix or every possible future branch.

Use only the supplied proposal, applicable owner rulings and general engineering knowledge. Use tools only to read what you were given; if it exceeds one read, read all of it in bounded pieces before judging. A truncated receipt is a delivery failure, not a proposal verdict. No code, raw reports, external research or other agents. Treat reported observations as premises, not the author's causal interpretation. Do not invent missing commitments, prior checks or product policy. Offer technical possibilities as questions, not findings. Acceptance does not certify the investigator's facts.

Read the opening as an owner unfamiliar with this subsystem. State its intended handling, observed difference, and what each proposed response would achieve. If that requires supplying missing background, guessing what the failure applies to, or treating a task label as its purpose, push back for a rewritten explanation. Facts buried in a stage inventory do not make the opening understandable. Check that essential terms are explained in the proposal itself; do not repair them from your expertise. Incidental expert details and minor wording preferences are optional.

Compare the proposed work with what can be done now. If it waits for data, symbols, reproduction or another party, consider retained evidence, source and contracts, applicable research and local experiments. Require a useful committed operation or a specific reason those available routes cannot help. You cannot check facts, so judge coverage. A proposal that substitutes reproduction, capture or waiting for available source/contract review must show in Known which files were read and a verdict for each owned stage; without that inventory, push back for static review. An investigation package that commits source/contract review as its first work can be accepted before that review is complete, even when a bounded reproduction is listed after it; what matters is that capture waits for the review's results. A design defect shown at an owned stage is grounds for fix now even while the incident's branch stays unattributed. Do not demand every method when one adequate route advances the decision. New capture must change a named decision, not replace available investigation without reason.

### Outcome and actions

Address each numbered question for the main failure and meaningful secondary concerns, wherever the proposal places the answers. “Unknown” is an answer only when it names the missing fact, what available evidence was checked, and which decision the fact changes. An inapplicable question needs a brief reason. Shared answers may cover several concerns.

1. **Cause and classification:** What starts the failure at this stage? Which checked reasons are accepted, which violate a contract, and which remain unknown or unmapped? Classify the reason and its handling separately: an accepted reason does not make its handling correct, and a known safe reason does not make every failure with the same event name safe. Use the reason established at the owning stage; accepting an outcome mapped there need not explain the external cause behind it.
2. **Design:** Can the owned code meet the required outcome on ordinary and interrupted paths? What differs from the applicable contract or a supported design for this product? Explain the fit and costs of the relevant choices, not a universal ideal. A different possible design alone is not a defect.
3. **User loss:** What stops working or is lost, for whom, how often and for how long? Is it temporary, persistent or irreversible? Separate measured impact from possible impact and unknown duration; row counts do not count failures.
4. **Recovery:** What restores the required user outcome, or ends the attempt safely? Was that outcome observed, checked only in source, or neither? What happens on exhaustion, cancellation, departure and another failure after recovery? A success callback, resumed unrelated work or ended attempt does not prove usable recovery.
5. **Feedback:** What does the affected user see while impaired and at the final outcome? Does it truthfully identify the unavailable capability and a usable next action? State any owner policy accepting silence, and its cost. Propose missing feedback separately; notification itself does not restore the capability.
6. **Evidence:** Can existing diagnostics identify the failing operation, stage, reason and relevant target, connect its attempts, measure loss, and distinguish recovery from abandonment or permanent failure? Name what engineering would do with each retained report. A report with no next action is noise; a missing one is a defect only when a decision needs it.

If the failure involves retry, reconnection or repeated recovery, also check reason selection, waits and spreading, limits and timeouts, reset after success, cancellation or target change, duplicate effects, and restoration of usable state, and what the user sees at first connection, during recovery and at terminal loss. Define the episode as first impairment until verified restoration or a named terminal ending; an application session is not one episode, and an attempt still active at shutdown or loss of telemetry has an unknown ending. When the decision needs the episode's duration or ending, evidence must show its start, changed cause, attempt count, elapsed time and ending; otherwise sparse evidence that answers the decision suffices. A rate limit must not hide a distinct cause, terminal failure or recurrence after recovery.

Select every supported response, each with its own outcome:

| Assessment result | Response |
| --- | --- |
| Checked code violates the required outcome | Fix the demonstrated defect; validate the affected user action. |
| The owner requested a design comparison, or a material uncertainty needs one | Commit the comparison now and name the choices and tradeoffs it will assess. |
| Remaining causes change the repair | Investigate with retained identifiers and evidence or an owned-input check; name which result selects which next action. A lookup that cannot be made leaves the cause unclassified, not proved absent. |
| Current evidence cannot distinguish cause, severity or ending | Repair evidence at the owner that knows it; name the missing fields or transitions and the decision they enable. No collection without a consumer. |
| User feedback is missing or misleading | Correct it, or offer an explicit policy choice with its user cost. |
| Exact reason and handling are accepted | Make the reporting decision explicit under the project's reporting policy: the exact predicate, which reports remain for unknown, unmapped, contract-breaking and still-actionable outcomes, and the visibility cost. |
| Existing design, evidence and feedback meet the goal | Retain them with evidence; do not invent work to fill every action category. |

A logging-only change or no action needs demonstrated contract compliance and, where a user loss or limitation remains, the recovery, fallback or feedback that handles it and the policy accepting what remains. Neither an expected trigger nor absent reported impact supplies that support. A wording change earns its place only if it corrects classification, identifies the next action or prevents a misleading user explanation.

For each separately approvable response, require its useful outcome and material cost. For a changed limit, timeout or retry delay, require what the value controls, the goal or contract it serves, why the proposed value helps, and its tradeoff. Distinguish a defect repair from an intended policy change; the latter needs a supported goal, not an invented bug. Honor an owner-selected mitigation without demanding an unproven alternative cause be excluded first. External ownership alone does not put the supported user experience out of scope.

Inventory the operations actually committed in the packet before judging omissions. Credit each explicit operation; "this could help" alone is not a commitment. A check whose outcome the proposal already predicts is not an operation either: push back when a test or reproduction cannot fail. For a single-session anomaly on a constantly exercised path, require the recovery question before a mechanism test, and credit a stated runtime assumption that classifies the stall as expected. When asking for an additional method, explain why the committed work is insufficient for the proposed outcome, rather than making your preferred method mandatory. For a referenced but unread task, ask for the next operation rather than imagining its contents. A reopening trigger alone is not a reason to do nothing now. A reopening trigger that no forwarded signal can show is not a trigger: push back for the observable signal, the diagnostic that would supply it, or an explicit acceptance that the condition will go unseen.

Check restrictions that strand useful work or permit unsupported closure. Separate the fact needed for safe action from the method proposed to establish it. For a disputed mandatory method, ask whether the fact can be established without that method at all. When a sentence requires several conditions, judge each one; one can be justified and another not. Choosing a reasonable first check or ordinary regression check is not an exclusive prerequisite unless the proposal says so. Reject restrictions only when they materially block useful action or license unjustified closure.

Read a fix-now recommendation against its Known: the mechanism must be a checked fact there, not a hypothesis written as one. Each entry in What does not fit must say what it would change; do not accept one waved away.

Keep judgment proportional. A missing machine blocks that run, not independent work. A negative check establishes only what was tested. A useful first package may leave cause, ownership and later actions undecided. Do not require an exhaustive future decision tree or stronger certainty than the proposed outcome needs. Do not ask for work that publishes private diagnostics or exceeds the requested scope. Classify an isolated secondary concern proportionately; it does not need an exhaustive investigation.

Return a brief verdict:

- **Accept** or **Push back**, with the essential reasons. Do not silently repair the proposal before accepting.
- Account for each meaningful concern's committed operation or evidence/cost reason for no action now. Combine concerns with the same disposition.
- If a material restriction is unjustified, quote it and name the necessary fact and the alternative route or contract at issue.
- State only essential repairs and what this package would establish or leave open. Mark preferences optional. Do not add a speculative technical explanation when the missing operation or false restriction already explains the verdict.

## Revise or rebut

Answer push-back by investigating and revising, or by rebutting with a reason. Change the work or its supported claims, not just how convincing it sounds. Send a revised proposal to a new judge. For a rebuttal without revision, record the dispute for the user; do not poll new judges for acceptance of unchanged work.

Use three reviews as the default budget unless the user sets another. If disagreement remains at that point, hand off the unresolved proposal and dispute, not an accepted outcome. Keep every verdict in the note. A later acceptance does not erase an objection that was rebutted rather than resolved; retain it for the user.

## Batches

The user-facing session retains the input list, groups related symptoms into provisional clusters without claiming a shared cause before investigation, and searches the project's tracker for existing issues on each cluster. Start one fresh investigator per cluster, in parallel. Give it the observation and the applicable project workflow and owner rulings. The observation contains templates, counts, examples, context and matching issues' observed impact. Exclude earlier dispositions and proposed next steps, which anchor the reading. Each follows this file and writes its proposal, returning the verdict and any dispute. An investigator that finds one cluster is two, or two are one, says so.

When a cluster's accepted proposal recommends reproduction, capture or waiting, or its fix changes a schema, a replicated protocol or a recorded ruling, start a second fresh investigator with the same project workflow and owner rulings, the observation and that recommendation, tasked to find a fix at the owner of the mechanism that is cheaper or removes the cause. Hand off both proposals. Spend this redundancy only there; it is where a first reading most often stops at the first workable design.

Reconcile cluster membership and shared follow-ups when assembling the batch list; a shared diagnostic task does not by itself establish a shared cause. List an outcome for every input, ordered by the project's priority convention, with the sources each cluster covers, the issue it relates to, its recommendation and its dispute appendix. Each case block is the writer's hand-off, judged under handoff.md; the writer receives the project's section meanings and chooses the section. Let the project workflow own layout and occurrence labels. Assemble the judged blocks. If assembly changes a block's meaning or section, return it to the writing judge. A material change to the technical proposal needs a new technical judgment and a new hand-off. Blocked work appears with its reason. Record the user's decision on each item with its reason, including a rejected push-back. A decision that states a standing preference becomes a rule in the document that owns the affected feature, written as the rule itself, so later judges receive it as an owner ruling and later investigators do not reopen it. The investigator's note and the batch list are enough for this loop; it adds no shared database.
