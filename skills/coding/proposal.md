# Judged proposals

Read when the user says `judged` or `with a judge`, or a workflow you are running names this file. Read it and [diagnosis.md](./diagnosis.md) before investigating. The investigator uses that file's shared assessment; the judge checks its application. This loop adds no ledger, runtime or coordinator; it does not replace obligations of an explicitly selected joint route. SKILL.md's Read for the work still applies to the investigator.

## One pause, then the work

Every cluster selected for a new assessment under Batches ends in a proposal with a recommendation, whether or not you could fix it now. A judge checks the proposal, a fresh writer turns the accepted proposal into the owner's hand-off under [handoff.md](./handoff.md), the batch lists every hand-off, and the user decides at that one pause. Ordinary implementation waits for that decision; when the user approves a fix or an investigation, do it under the run's authority with the ordinary change review. Filing an issue records the proposal; it does not handle the incident. When the user asks to file, publish under handoff.md, Publishing as an issue or comment.

Judge acceptance assesses a next action. It grants no authority to implement, publish issues, close incidents or expand scope. Follow the user's requested stopping point and the project's approval boundaries.

Implementation of an approved proposal starts by checking each fact in its Known against the current code. A fact that no longer holds returns the proposal to its investigator before any edit; this narrow check is cheap and catches both drift and a shallow claim.

A candidate experiment before the pause is allowed only when it is the cheapest way to prove a mechanism. Keep it out of the checkout and report it in Known as evidence.

Recommend the next step supported by diagnosis.md's shared assessment, including its Forwarded-log triage rule when applicable. An investigation proposal commits to resolving its deciding question; it need not select the eventual implementation. A demonstrated repair need not wait for unrelated unknowns.

## The proposal

Lead with diagnosis.md's compact decision summary. First explain the normal operation and intended handling, then the observed difference and why it needs attention. For each separately approvable response, explain what it changes and why that helps. A list of engineering tasks does not supply this explanation.

Define a term when its meaning determines the decision. Spell out essential acronyms. Introduce file names, flags, stage inventories and incident counts after the reader understands the situation and response. Use the project's issue format when it defines one; every slot below still appears under some heading.

- **What happened.** The ordinary situation, its intended outcome and the observed difference, in language the owner can follow without subsystem knowledge. Say whether handling is defective, expected or still unclassified, and why the proposed attention is worthwhile. Include symptom, user consequence, meaningful secondary concerns, reach with its window and counting limits.
- **Known.** Checked facts and their sources, separated from hypotheses. Name the files read and the changeset. Give a verdict for the owned stages and inputs that determine the observed failure and recommended next action. Name uninspected areas as limits. A next-action triage is not an exhaustive design audit; broaden only when another input or stage could change that decision. A stage shown unable to handle the observed state under the stated contract is a checked mechanism and supports fix now; use diagnosis.md for the response's independent basis.
- **Assessment.** Answer diagnosis.md's Concerns using its shared evidence and inapplicability criteria. Answers may share prose or reference Known. Keep these answers here, not as a questionnaire in What happened.
- **Unknown.** State whether the relevant target or file is identified, available and already tested, with the result and its limit. If known, name the retained identifier and the completed check and its result, not merely “available”. Separate an unavailable historical fact from a field missing only in future reports. Then list the questions that affect the next decision, what has been tried, and what blocks answering them now from the code and evidence you had. "Not enough evidence" alone is not a blocker, and a limit of the telemetry is a blocker only when the code at that changeset cannot answer the question either.
- **What does not fit.** Observations that weaken this explanation or could change the recommendation, each with what it would change, or `none`. Never omit one because the judge could not evaluate it.
- **Recommendation.** Apply diagnosis.md's Responses and give each selected response its disposition. State the committed operations and what they establish or improve; "could help" alone commits no work. Name the strongest alternative considered and why it lost, or the checked facts that leave no competing action-changing alternative. Link an existing issue when it applies, or recommend creating, updating or reopening one when recording follow-up is useful. Keep the response's benefit distinct from that tracking decision. A bounded investigation needs its deciding question and available input, not a specification of the eventual implementation. In forwarded-log triage, give each selected response the fields diagnosis.md's response table names, as a table.
- **Scope and risk.** Boundaries and owners touched, relevant support or owner constraints, tradeoffs, the main regression or validation risk, and the kind of evidence that will establish completion. Design the implementation and its fixtures after approval; include detail now only when it determines feasibility, scope or the owner's choice.

Apply diagnosis.md's Completion rule. The required technical coverage stays in this proposal. The owner's hand-off is a separate text that a fresh writer produces from the accepted proposal under [handoff.md](./handoff.md); the investigator does not write it, and answers the writer's questions about an unclear or contradictory claim. Keep the investigation narrative, evidence dumps, earlier revisions and verdicts in your note. Put unresolved or rebutted objections in a separate dispute appendix for the batch list, never in a judge's or writer's packet.

## Dispatch the judge

Start a fresh agent for each proposal revision. A revision changes a claim in Known, a committed operation or the recommendation; a wording or reference correction the judge asked for is applied and recorded beside the accepted verdict without a new judge. Give it only The judge section below, diagnosis.md from Shared assessment through the end of that file, the current proposal, and the applicable owner rulings, taken from the documents that own the affected feature and from the user's decisions at earlier pauses. When the proposal adds, changes or retains failure evidence, also include [logging.md](./logging.md). Do not include prior verdicts, the dispute appendix, code, raw reports or your note. Deliver the packet inline or as one file whose length you state, so the judge can tell that it received all of it. Wait for its verdict before advancing that cluster's dependent step. Fill available agent slots with ready work as results arrive; another cluster's investigation or blocked lookup is not a stage-wide barrier. Use agent-messaging when available.

After Accept, dispatch the writer, then the writing judge, each a fresh agent with the packet handoff.md names. A writing push-back returns to the writer; a contradiction the writer finds returns to the investigator, and a changed claim is a new proposal revision for a new technical judge.

Keep review status outside the candidate text. Each status is Pending until you have read the returned verdict for that exact revision. In the batch list, show the technical verdict and the writing verdict separately, each derived from its recorded verdict with a link; a planned review or another revision's acceptance supplies neither. Updating a status after the result does not require judging again. Record the exact packet and verdict with the revision in your note, then close the disposable session.

## The judge

Decide whether this proposal meets diagnosis.md's response and completion rules for the task. You judge the next work package, not a final fix or every possible future branch.

Use only the supplied Shared assessment, logging.md when included, proposal, applicable owner rulings and general engineering knowledge. Use tools only to read what you were given; if it exceeds one read, read all of it in bounded pieces before judging. A truncated receipt is a delivery failure, not a proposal verdict. No code, raw reports, external research or other agents. Treat reported observations as premises, not the author's causal interpretation or claim of a violated requirement. Check the assessment's evidence, response and completion criteria against those premises. Do not invent missing commitments, prior checks or product policy. Offer technical possibilities as questions, not findings. Acceptance does not certify the investigator's facts.

Read the opening as an owner unfamiliar with this subsystem. State its intended handling, observed difference, and what each proposed response would achieve. If that requires supplying missing background, guessing what the failure applies to, or treating a task label as its purpose, push back for a rewritten explanation. Facts buried in a stage inventory do not make the opening understandable. Check that essential terms are explained in the proposal itself; do not repair them from your expertise. Incidental expert details and minor wording preferences are optional.

Compare the proposed work with what can be done now. If it waits for data, symbols, reproduction or another party, consider retained evidence, source and contracts, applicable research and local experiments. Require a useful committed operation or a specific reason those available routes cannot help. You cannot check facts, so judge coverage. A proposal that substitutes reproduction, capture or waiting for available source/contract review must show in Known which files were read and a verdict for each owned stage; without that inventory, push back for static review. An investigation package that commits source/contract review as its first work can be accepted before that review is complete, even when a bounded reproduction is listed after it; what matters is that capture waits for the review's results. A demonstrated violation at an owned stage can justify fix now without attributing the incident, when the proposal establishes the required behavior and value of that repair independently. A merely possible cause does not establish either. Respect a scoped owner decision to investigate or defer. Do not demand every method when one adequate route advances the decision. New capture must change a named decision, not replace available investigation without reason.

Check every applicable concern and response under the supplied Shared assessment, wherever the proposal places its answers. In forwarded-log triage, check each selected response's fields against the response table before reading the prose: a Suppress without the unclassifiable-input field, a Diagnostics value with no selected action or with overlapping rows, or a completion counted in future reports is a push-back. Account for meaningful secondary concerns as well as the main failure. Credit shared answers when their facts cover those concerns; a role name or unsupported inapplicability assertion does not supply that coverage.

Inventory the operations actually committed before judging omissions. Apply the shared standard for deciding checks and required validation. When asking for another method, explain why the committed work is insufficient for the proposed outcome, rather than making your preferred method mandatory. For a referenced but unread task, ask for the next operation rather than imagining its contents.

Check restrictions that strand useful work or permit unsupported closure. Separate the fact needed for safe action from the method proposed to establish it. For a disputed mandatory method, ask whether the fact can be established without that method at all. When a sentence requires several conditions, judge each one; one can be justified and another not. Choosing a reasonable first check or ordinary regression check is not an exclusive prerequisite unless the proposal says so. Reject restrictions only when they materially block useful action or license unjustified closure.

Read a fix-now recommendation against its Known: the mechanism must be a checked fact there, not a hypothesis written as one. Read What does not fit against Known and name a statement that contradicts Known; it is a text correction, not a push-back unless a committed operation depends on it. Each entry in What does not fit must say what it would change; do not accept one waved away.

Keep judgment proportional. A missing machine blocks that run, not independent work. A negative check establishes only what was tested. A useful first package may leave cause, ownership and later actions undecided. Do not require an exhaustive future decision tree or stronger certainty than the proposed outcome needs. Do not ask for work that publishes private diagnostics or exceeds the requested scope. Classify an isolated secondary concern proportionately; it does not need an exhaustive investigation.

Return a brief verdict:

- **Accept** or **Push back**, with the essential reasons. Do not silently repair the proposal before accepting.
- For each separately approvable response, state the required outcome and its source, and whether the evidence suffices for that next action. Account for every meaningful concern; combine responses with the same basis.
- If a material restriction is unjustified, quote it and name the necessary fact and the alternative route or contract at issue.
- State only essential repairs and what this package would establish or leave open. Mark preferences optional. Do not add a speculative technical explanation when the missing operation or false restriction already explains the verdict.

## Revise or rebut

Answer push-back by investigating and revising, or by rebutting with a reason. Change the work or its supported claims, not just how convincing it sounds. Send a revised proposal to a new judge. For a rebuttal without revision, record the dispute for the user; do not poll new judges for acceptance of unchanged work.

Use three reviews as the default budget unless the user sets another. If disagreement remains at that point, hand off the unresolved proposal and dispute, not an accepted outcome. Keep every verdict in the note. A later acceptance does not erase an objection that was rebutted rather than resolved; retain it for the user.

## Batches

The user-facing session retains the input list. For forwarded-log batches, first apply diagnosis.md's pending-issue filter before clustering or dispatch. Continue covered inputs directly in the existing issue; dispatch no investigator, writer or judge and create no new proposal for them. Group the remaining inputs into provisional clusters without claiming a shared cause before investigation, and search the project's tracker for existing issues on each cluster. Start one fresh investigator per cluster selected for new assessment, in parallel. Give it the observation and the applicable project workflow and owner rulings. The observation contains templates, counts, examples, context and matching issues' observed impact. Exclude earlier dispositions and proposed next steps, which anchor the reading. Each follows this file and writes its proposal, returning the verdict and any dispute. An investigator that finds one cluster is two, or two are one, says so.

Start a second fresh investigator only for an unresolved alternative that could change the next action, affected scope or material cost and has not already been evaluated. State that deciding question before dispatch. Reproduction, capture, waiting and schema or protocol changes prompt this check; none alone requires another investigation. Give the investigator the observation, proposed recommendation, applicable rulings and the specific alternative question. Reuse checked evidence and inspect only what could decide that question. Retain the comparison and any changed recommendation. A confirmatory rereading without a deciding question earns no second pass.

Keep ready, dispatch and returned-verdict times with the existing revision record, reusing tool timestamps. This distinguishes queue delay, blocked evidence and review work without a separate status document.

Reconcile cluster membership and shared follow-ups when assembling the batch list; a shared diagnostic task does not by itself establish a shared cause. List an outcome for every input, ordered by the project's priority convention. For pending-covered inputs, list the existing issue and continuation status without a new decision or judged hand-off. For newly assessed clusters, list the sources covered, related issue, recommendation and dispute appendix. Each new case block is the writer's hand-off, judged under handoff.md; the writer receives the project's section meanings and chooses the section. Let the project workflow own layout and occurrence labels. Assemble the judged blocks. If assembly changes a block's meaning or section, return it to the writing judge. A material change to the technical claims, recommendation or supporting facts needs a new judgment of the affected claims and an updated hand-off; unrelated accepted cases stay settled. Blocked work appears with its reason. Record the user's decision on each item needing one with its reason, including a rejected push-back. A decision that states a standing preference becomes a rule in the document that owns the affected feature, written as the rule itself, so later judges receive it as an owner ruling and later investigators do not reopen it. The investigator's note and the batch list are enough for this loop; it adds no shared database.

## Clarifications at the pause and after

Answer the user's clarification or alignment question directly from the checked facts and their words before refreshing saved artifacts. A user decision settles that choice; another judge need not ratify it. Record the decision and its scope. Reopen technical review only when a changed recommendation, claim or supporting fact needs a new owner decision, and review the changed part. Re-run writing review when a materially revised hand-off will be used for that decision or published; an immediate clarification does not require a new writer, judge or second investigator. Preserve accepted evidence and disclose any remaining technical dispute.
