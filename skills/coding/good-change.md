# Good change

Design and boundary judgment for implementation, review and diagnosis. These principles apply at every level. SKILL.md owns read selection, authority and the selected level. For deep work, investigation.md owns the method.

## Establish the outcome

For a feature, identify the intended experience and the scenarios that distinguish success from a merely completed implementation. Separate user rulings from implementation choices. For a defect, identify the bad state and the mechanism that produces it. For a maintenance change, name the concrete task or failure boundary made easier to reason about. Do not invent a bug to justify a requested feature.

Read the producing operations and the branches that consume their answers before selecting the boundary. Establish what each return value means through completion, cancellation and cleanup, including one level into a consumed provider. For a changed shared result or classification, enumerate its callers and inspect the interpretations the change can affect. Check existing docs, tests, and retained captures before calling a behavior blocking or untested; incidental coverage counts only when the artifact shows the relevant state. Keep an acceptance explanation proportional to the choice the user needs to understand.

## Name the fact before storing it

Before the first edit, and in a proposal or review of a change, sweep the facts the change stores or rewrites: a stored field, flag, count or map entry it adds, an existing one whose meaning or writers change, and a public entry point that writes one. An empty sweep needs no note. Otherwise write a structure note in the response, before the plan: one table, one row per fact, with these columns.

When these source checks span separate provider or subsystem contexts, the agent assembling the structure note partitions them into bounded parallel subagent assignments. Each assignment supplies the goal and rulings, selected level, contract questions, source paths and applicable guidance paths; the worker reads that guidance before inspecting source. Source workers return the inspected producer, writer and consumer paths, the enforcing predicate or a counterexample, and unresolved cross-context facts with their deciding checks to that agent. It collects those returns and addresses status or shutdown using worker identities returned when launching the assignments, follows the shared interaction and reconciles the findings into this table and its implementation plan before editing. These are source checks within the selected level.

- **Fact.** What runtime question does the value answer, and which named consumer branch uses it? State its kind: a decision a person made, an observation of a process or device, the outcome of a request, or a value derived from other rows. For an observation or outcome, name the states consumers must distinguish and the condition making each answer valid. A decision names its originating action and scope. A request's status from start to completion is one outcome row even when a person started it. A source or a reason is not the fact: "the position the editor sent" names who supplied an input; the fact is "where this item currently is".
- **Writers.** Which operations write or rewrite the value, from which inputs? Include existing refreshes, initialization, deferred completion, cancellation and cleanup that can replace the answer, as well as the operations the change adds. Read existing signatures and bodies and identify where planned writes will run; a callback or method name does not establish completion.
- **Lifetime and cardinality.** Does storage outlive each party that sets or uses it, and can several instances be live at once? Name those parties. For deferred work, inspect identity reuse, delivery order, cancellation guarantees and reentry. A kind, reason or category is not an instance.
- **Held.** What exact invariant must hold for those consumers, and which type, predicate or operation enforces it? Name its source location and follow ordinary and interrupted paths through it. Classify enforcement as unrepresentable by type, refused at one gate, or a runtime check, with the reason a stronger level is unavailable. A check each caller must remember is a runtime check, not a gate; a comment or convention is no level at all.
- **Verdict.** Either "the existing structure holds this fact", with the source paths proving it for the affected consumers, or the API change to make first, listed as the first step of the plan. Settle an unknown producer or consumer contract by its deciding source inspection or check before assigning the verdict. An unavailable prerequisite remains an explicit limit under SKILL.md.

Apply every matching rule to each row. A row that matches a rule's defect condition has an API-change verdict, not "holds":

- Two writers that each compute the value from a different source, so the stored value depends on which ran last: one owner writes it, the others preserve it or ask it. Last writer wins is not a resolution; a refresh that re-derives the value from its own source overwrites what the other writer set.
- A writer that reloads the value a decision's action saved is restoration and preserves the decision; cancellation or expiry ends its authority. An observation or completion that creates, renews or retargets the decision writes a fact it has no authority to decide. A callback completing the request that the action started writes the request's outcome, which is a different row.
- A party that can outlive its storage, such as a request still waiting while the record it was keyed to is removed and recreated, needs its own handle, and release takes the handle, not the key. A key, or a count keyed by it, frees whoever holds that key now and cannot tell a stale release from a live one.
- A writer that appears in two rows writes two facts. When the writes keep one invariant of one owner, such as a list and its counts updated under the same lock, the rows share a verdict and may hold. When the facts answer independent questions, such as a setter that also re-derives a neighbouring value from its own source, it is two operations: split it. When the second fact belongs to another owner, such as a release that also decides what happens next, it is a leak: move it.
- An operation whose name or parameters carry a caller's reason (which tool asked, which phase of an edit, cancel against commit) is a boundary leak. Rename it after the fact it writes, keep the reason and sequence in the caller, and state in one sentence what the caller must still know and do.

For each API-change verdict, name the strongest simpler alternative and the bug class it leaves possible; a note whose rows all hold names none.

## Choose the boundary

- **Fix the cause where it can be owned.** When a failure reaches a guard or log, trace its input through the callers to the producer before choosing the fix. Distinguish a failed retrieval, missing validation, and an external failure; each has a different owner. Correct an owned producer or caller now instead of adding diagnostics to discover a path the code can establish. Validate uncontrolled input where it enters. If the cause remains unknown or outside your control, name that limit and restore the user outcome the application can own.
- **Describe collaboration before states.** For a protocol or lifecycle change, walk an ordinary case and an interrupted case in domain terms: who does what, what they wait on, and what changes under them. Map implementation states to the decisions or observations they serve. Do not add states merely to represent stages of your investigation.
- **Put decisions at the boundary that can own them.** Name the domain decisions and invariants affected by the change and who owns each. Before adding a guard, recheck, sequencing rule, failure classification or recovery that another caller already performs for the same fact, compare owning it at their common operation. A second copy of a guard is the cue that the rule's owner is wrong, not that a caller was missing it. Keep independently changing policies separate; keep one policy's enforcement together. Trace dependencies between domain policy, presentation, persistence and external services: a change to a delivery detail should not require rewriting the domain decision. Introduce a contract when it removes a concrete dependency or protects an invariant, not merely to put an interface in front of a class. Verify which paths the owner covers and what bypasses it. Compare total responsibility and caller effort, including any failure mechanism the structure can remove.
- **Reuse before adding.** Look for the same job in the owning module and existing libraries. Share an abstraction when its callers share a contract and should change together, not merely similar lines.
- **Price the costs that remain expensive.** Generation and reversible experiments are cheap; regression risk, integration, interface churn and future readers' reasoning are not. Neither preserve a bad structure solely to minimize the diff nor expand a working change solely because another design exists.
- **Sweep the mechanism.** Inspect sibling sites that share the cause, contract or workaround before claiming the class is fixed. Broaden the sweep only when it can change that claim or the fix boundary.

## Check the result

Disproving one proposed cause does not resolve the observed failure. State what remains unexplained and the observation that would distinguish it.

Choose checks for the actual claim. A defect reproducer before and after the change is useful when it distinguishes the cause and correction. A structural change may need preserved-behavior checks and an ownership argument; a feature needs acceptance scenarios. Do not manufacture a red run for a claim that predicts no behavior change, or present a replica as tested production wiring.

Inspect the resulting diff and affected failure paths against the structure note's invariants and named enforcement sites when a note exists; otherwise check the requested behavior and its relevant contracts. Explain material departures from the chosen boundary and their effect on the requested outcome. For a failure-handling change, state the cause repaired or the limit that remains, the shared handling owner, and evidence of what the affected user action now does. Verify that action reaches its intended outcome; a quieter log, propagated error, or shared callback alone does not establish it. A failing check identifies the contradicted invariant and the path to correct. When an approach fails, preserve a useful result and its reason if later work would otherwise repeat it.

Independent review follows the procedure selected in SKILL.md. Explicit code reviews use review.md; ordinary implementation self-checks do not launch a verifier automatically. Preserve the rationale for the user. A preference without an unmet obligation is not a condition.
