# Goal

Why this skill exists, what it values, and why its features have their shape. Read before discussing or changing it, and let every suggestion follow it.

## Why

One skill serves review, diagnosis, and writing because they share the same project, evidence, and judgment. It is designed for agents doing real work: writing code is cheap, while human attention, trust, and lost context are expensive. The standards travel across projects; the design choices depend on the project's goals and constraints.

## Values, in the order they win

1. **The right behavior, supported by evidence.** Correctness means meeting the feature's goals, intended user experience, explicit human rulings, and real system contracts. Reliability includes recovery and an honest, usable outcome when an external prerequisite cannot be restored. Evidence must distinguish the claim from an alternative that would make it wrong. Execution, measurement, and code proof answer different questions; agreement alone answers none.
2. **The user can trust, understand, and steer the work.** In fix mode, agents own the recoverable candidate, including redesigns and changes to related systems needed for the goal. They develop and validate it; the user judges the result and can redirect or reject it. Candidate breadth is not a permission boundary, and peer agreement is not user acceptance of its tradeoffs. A long agent-written spec is not evidence that a human decided every detail in it. The user sees consequential choices, uncertainty, and why a change took its shape, without having to read the whole investigation. Explicit prohibitions and effects outside recoverable local work still need their own authority.
3. **The project stays understandable.** A later reader has less context than the agent that wrote the code. Ownership, state changes, contracts, and failure outcomes should be clear from the code and its named interfaces. Evaluate simplicity across the subsystem and its callers, not just interface size or lines deleted. Complexity earns its place when its contribution to a present obligation or a clearer design justifies its costs.
4. **No wasted work or attention.** Within those values, remove waiting, repeated discovery, and ceremony. Code generation and reversal are cheap; regression risk, integration work, and human comprehension still cost something. Scale records and checks to the decisions and risk, not the number of agents or lines changed. A mechanical correction needs direct validation, not the full candidate workflow. A step earns its place by reducing a concrete uncertainty or preserving information, not because human-written code used to pass through it.

## How we think about the workflow

- **Explicit levels, light by default.** Normal coding applies project knowledge and good-code principles, makes the requested change or assessment, and checks what needs checking. The user's directive `deep` or `deeply` adds the investigation method. Deep work explicitly requested with two or multiple models selects joint investigation. Risk, task size, the word "bug", and requests to be thorough do not select a heavier level. The level persists through that task until the user changes it; a new standalone task defaults to normal. These are choices of method and coordination, not different standards of honesty or correctness.
- **Common judgment before method.** Substantive code work reads code-quality and change-design guidance together: reviewing existing choices and proposing remedies need the same design judgment as implementing them. Language and engine guidance stays conditional. Specified mechanical and presentation edits do not need this shared reading step.
- **Name the fact before storing it.** Given a feature, an agent reaches for a new input into an existing store: a flag beside the flags, a second copy of a value beside the first. The bugs that follow are two writers disagreeing or a holder outliving its storage, and review rounds find them one at a time. A change that adds state or an entry point, or gives an existing fact a new writer or meaning, therefore writes a short structure note before the first edit, one row per fact. Source checks establish producer semantics, writers, consumer interpretations and enforcement; separate owner contexts contribute to one converged note. good-change.md owns its columns and the rules that turn a row into an API change. The API change to make first is then proposed with the feature rather than after its third fix. Implementation checks establish that the chosen invariants hold in the resulting code.
- **Diagnosis seeks useful improvement.** An unresolved incident can still support safer handling, bounded mitigation or evidence that makes the next decision possible. Forwarded-log triage must change the failure, improve the deciding evidence, or keep verified non-actionable reports local. Existing pending work owns its collection and decision bounds; its reports do not need repeated triage. Recurring engineering attention is a cost, not a permanent disposition. General assessment and review can still find that no change is needed. Documented failure semantics and static source/configuration checks establish what can improve now; attribution and a complete cause fix are separate results. Failure evidence follows the operation and answers a decision at the stage that owns the facts. Retry and recovery need an explicit episode boundary and ending, or an explanation of how existing operation evidence suffices. The diagnosis reference owns the shared questions and response selection in investigator voice, at every level. Each applicable concern has its own supported response; several actions can help the same incident. Normal work keeps these answers in its existing report or note. The logging reference owns evidence design; architecture extraction records the corresponding evidence in its own portable skill.
- **Procedure resolves uncertainty.** A check earns its place by answering a real question about the requested result. Normal implementation and diagnosis need no mandatory investigation dossier, capture runner, independent reviewer, or before-and-after ritual. An explicit code review selects work from factual conditions, investigates it, then gets fresh verification of coverage and conclusions. The main agent may investigate or delegate; answer provenance preserves responsibility without imposing an investigator count. Fresh verification supplies the distinct checking role. Separate scope and coverage agents add no required role. Deep work retains the cause, evidence, candidate and remaining uncertainty. The ledger does not certify that a bug exists or a fix works.
- **Information continuity.** Normal work retains a short continuation note only when unfinished work needs it. Deep investigation keeps an evolving note and useful artifacts so context loss does not discard reasoning or repeat discovery. The database is reserved for joint investigation: versioned commitments, ownership, waits, independent assent and attention across actors. Neither a substantive edit nor a long solo investigation selects it. When the user changes level, carry applicable work forward instead of restarting to change record formats.
- **Review policy is selected, not invented.** Review questions and responses come from the selection table in good-code.md. Agents establish which facts hold and apply every matching rule; they do not choose a preferred amount of coverage. Unknown applicability remains work. Evidence must support clean results as well as findings. A fresh verifier selects from the original target before seeing the investigator's answers, then checks those answers and returns concrete omissions or contradictions. This reduces both inherited blind spots and unsupported findings without a separate planning audit.
- **Independent perspectives serve distinct decisions.** Explicit code reviews use fresh verification without selecting joint investigation or requiring a database. Implementation self-checks and standalone diagnoses do not automatically launch reviewers. Joint investigation uses different model families because they can discover different problems and challenge each other's assumptions. The user chooses the joint investigator models and effort settings; the skill supplies no defaults for them. Ask for missing choices before starting those investigators. Preserve independent first readings and the author's rationale. Bounded subagent work does not itself select joint investigation.
- **A proposal is judged by a reader who sees only what the user would see, and the user decides once per batch.** Every cluster ends in a proposal with an honest recommendation, including a fix the investigator could make now. A fresh judge checks the shared diagnosis standard against the exact proposal with applicable owner rulings: no code, no note, no earlier verdicts. The investigator uses that standard before proposing work; the judge checks its application rather than defining another standard. It stands in for the user's first reading, so the user's attention goes to disputes instead of repairing plausible proposals. Because it cannot check facts, the proposal makes its coverage legible: which owned stages were read and judged, and which alternative lost. A second investigation answers an unresolved alternative that could change the next action, scope or material cost; waiting alone does not trigger one. Triage stops under diagnosis.md's completion rule before designing the implementation. A clarification receives a direct answer before any artifact refresh, and a user decision does not need another judge to ratify it. The owner's hand-off is written by a fresh writer from the accepted proposal, not by the investigator: a context full of the subsystem's vocabulary produces a compressed proposal, not an explanation, and asking it to preserve every limit makes the text shorter without making it clearer. Its title and opening expose the nature of the proposed action so the owner can tell a functional repair from evidence or reporting work before reading the detail. A writing judge reads the hand-off alone first and checks that it explains the owner's decision under handoff.md before comparing it with the proposal. Ordinary implementation follows the user's batch decision, so no agent authorizes its own fix by calling it concrete. Acceptance belongs to one exact revision. One investigator, one disposable judge, one writer, one writing judge and a note need no ledger or runtime.
- **Execution facts come from execution.** Consume actual results before interpreting them. Deep investigations capture command, returned bytes and termination at the process boundary so evidence can be inspected later. A capture does not certify a test's assertions, the engineering claim, or prose written before that result arrived. Normal work can use its ordinary tool results without this helper procedure.
- **Keep pushing on the concepts.** Read retained work for where time and information were lost. Rethink the shape before adding a step. In joint work the database keeps the shared sequence of decisions; its timeline distinguishes recorded actions from inferred activity. Artifacts retain the detail needed to resume without loading it all into every agent's context.
- **Trials serve the skill.** When a real task is being used to test this skill, the task is the workload, not the objective. Capture a meaningful workflow failure and stop the trial automatically; preserve its unfinished work and repair the skill before running another bounded check. A successful workload does not excuse a broken workflow.
- **Equal investigators, shared conclusions.** In a joint run the investigators pursue the same evolving investigation with equal authority to investigate, implement, challenge and ask the user. Temporary action ownership prevents interference; it does not appoint a primary investigator. Substantive conclusions and replacement explanations need both investigators' agreement, not permission before each experiment. Publishing a conclusion endorses it; a material revision clears the peer's agreement. Evidence and checkpoints alone are not endorsements.
- **Tasks and dependencies, with room for judgment.** Tasks state the results owed; dependencies state which task results are needed. Agents claim useful available work and choose how to carry it forward. Ownership, evidence, authority and execution facts support that work without prescribing engineering phases. The script preserves those facts and derives availability; investigators judge whether a result meets the goal, what a changed input affects, and how continuing work accounts for the original concern.
- **Explain purpose and boundaries.** Guidance gives agents the goal, the reason a distinction matters, and where their judgment applies. Exact constraints earn their place when they protect work, authority, execution or evidence. Prefer removing an unnecessary concept to adding a rule about how to manage it.
- **Visible outcomes.** Conclusions, replacements, cancellations and consequential blockers reach the master's attention even while other work continues. Keep the monitor beside the master without crowding the conversation, and give the investigators equal space together. The master reads their reasons and summarizes meaningful outcomes for the user; acknowledging a report is not agreement with its engineering claim.
- **Recording is not delivery.** Investigators save work without depending on runtime messaging permissions. One coordinator observes current work and bound agent state, wakes idle agents when useful, and retains delivery uncertainty. Busy agents pull their next work; an accepted wake is not progress, and a pause is not an invitation to restart.

## What we do not do

- **Each concept serves the skill's purpose.** Keep a concept only when it contributes to the coding judgment or workflow this skill exists to provide. If removing it loses no needed capability, evidence or continuity, leave it out; being sensible practice elsewhere is not enough. For example, recoverable work and knowing which code was checked serve the investigation, while a project's commit procedure or business release policy does not need to be prescribed here. Scripts hold durable state, enforce checkable boundaries, and deliver messages; agents own engineering judgment. Use the smallest mechanism that meets the actual obligation, not speculative machinery.
- **No perfect-design search.** A different possible design is not a defect. Reopen settled work for new evidence, a changed dependency, or a human ruling. A remaining concern must say what observation or decision would resolve it.
- **Docs do not carry history.** They say what to do, in plain words defined once.
