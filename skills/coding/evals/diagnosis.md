# Failure diagnosis and useful improvement

Read when maintaining diagnosis.md, the proposal opening or the corresponding technical judge questions. Keep this answer key outside investigator and judge packets. Freeze expected behavior before running; retain exact guidance, prompts, outputs and checked sources outside the published skill.

The judge packet is defined in [proposal.md](./proposal.md), Judge packet. Every judge trial below sends that packet, the case text and the applicable owner rulings, and nothing else.

Use the same frozen case text and the same frozen candidate guidance for every model under comparison. A pre-change success establishes baseline capability, not an improvement caused by the instructions. Judge coverage and factual limits, not agreement with the skill author's preferred remedy.

## Investigation

Give fresh contexts the coding skill and one case from [diagnosis-cases.md](./diagnosis-cases.md), stopping before Judge inputs. Ask for diagnosis and a bounded proposal without supplying the expected response. Run D1 with only its incident log and read-only source/configuration access; previous investigation conclusions cannot substitute for the work. Normal diagnoses exercise diagnosis.md, and logging.md where evidence design is in question. Separately run a fresh D2 investigator explicitly assigned a **judged diagnosis**, with the investigator role ending at its technical proposal; the harness supplies the judge. Inspect that it reads proposal.md before investigating and produces the decision summary and recommendation rationale. Supply that exact proposal and applicable owner rulings to a fresh technical judge with the judge packet. A normal diagnosis does not test the proposal route by implication. Public official research is allowed, live services and product edits are not. This is a skill trial: stop on a meaningful workflow failure rather than finishing product remediation.

- **D1, original class:** distinguish completed HTTP refusal from transport or disk failure. Discover the provider chain from source/configuration, research applicable official error semantics, and assess existing diagnostic facilities. Propose useful present work if justified without attributing the historic refusal. Explain which provider alternatives proposed fields distinguish and which still collide, including generic errors. A request ID supports correlation, not attribution. Source configuration is not deployed proof; current configuration is not historic proof. A fully researched response may differ from an earlier recommendation. D1 runs against current real source: when the source already selects the detailed result, request and timing fields, proposing those fields again fails, and the useful work is validating their actual delivery or another independently supported response.
- **D2, unseen sibling:** use official PostgreSQL error/connection guidance and checked pool configuration. The permitted aggregate pool size can exceed the server cap; that establishes a configuration risk or comparison worth doing, not actual incident occupancy or a leak. Propose a bounded comparison, capacity/ownership mitigation or evidence improvement with explicit tradeoffs and validation. Distinguish current static knowledge from missing historical occupancy. Unknown occupancy must not prevent all useful work; the generic connection error does not select a particular capacity remedy.
- **D3, near negative:** retain verified intentional handling. Do not invent provider research, telemetry, retries, a limit change or a mandatory artifact.
- **D4, known-good:** preserve the adequate recovery/evidence path. Unknown internal provider attribution need not be resolved when it changes no remaining action; no new collector or retry change is justified.
- **D5, non-service regression:** no provider or library error exists, so documented-semantics research is inapplicable and the output says so with that basis. The case describes the two changes without their implementation, so the output commits bounded static review or spec work on them as its first operation and claims neither a read of absent code nor proof of either candidate. The cause stays unattributed between them, and the output still names the useful work: a deciding check that separates the two candidates on the low-end profile, with the result that selects each next action; an evidence or measurement package that would answer the decision (per-stage timing, a local profile run, or another supported route), with the decision it enables; gating or reverting the warmup pass as a product choice with its cost, offered as an alternative rather than recommended by default. Waiting for more total-load rows fails, because more rows cannot separate the two candidates. Prescribing one instrumentation implementation is not required.
- **D6, known cause with a secondary obligation:** the null dereference is a checked mechanism and the repair is recommended now. A fix-only answer fails. The output also accounts for the finance import that silently reads yesterday's file (recovery or feedback at the consumer, or an explicit owner policy accepting it), and for the Error that omits the order identifier (an evidence improvement with the decision it enables, or a reason it is not needed). A known cause does not make those concerns inapplicable.
- **D7, simple deterministic repair:** the harness supplies the helper and its failing test in the trial's private directory, and the case text permits edits there. The off-by-one is corrected in that fixture and the existing test is run and its result read. The report closes the remaining concerns in a few sentences with the facts that close them (the fix lands before any release; the helper has no retry, user feedback or telemetry path). A separate assessment document, a checklist table, provider research, new telemetry or a reopen signal for every alternative fails. The repair and a brief close is the expected output.
- **D8, unsettled framing:** question whether the retries violate required freshness or another established obligation before choosing a replacement architecture. Propose a bounded check of requirements, served-data age and the producer/consumer path, with results that distinguish accepted delay from needed handling or design work. Keep the architecture undecided; neither no reported harm nor the issue's proposed remedy settles the question. Do not invent source inspection or expand into a general catalog audit. D3/D4 must still close without invented questions, and D6 must still recommend the demonstrated repair without waiting for unrelated unknowns.

### First-draft coverage

Inspect the investigator's first output, before any judge correction. For each case, every applicable concern (cause and classification, design, user loss, recovery, feedback, evidence) is accounted for, and each selected response carries its own disposition in diagnosis.md's words: now, a bounded investigation with its deciding question and available input, blocked on a named owner decision or prerequisite, or retained or deferred with the accepted cost and the observable signal that reopens it. A concern the failure plainly does not involve needs no mention; one a reader could expect closes with the fact that makes it inapplicable. Shared prose and shared facts may cover several concerns and response rows, and an unused response kind needs no row. A global no-change summary is acceptable after those closures; a global verdict standing in for them fails. The answers live in the report or the existing note; a case that fits in a few sentences stays there. In a normal report with no action-changing uncertainty left (D3, D4, D7), reproducing the concern list as a questionnaire, listing unused response kinds, or appending the judged proposal's five-question summary is a presentation failure even when the actions are right.

## Technical judge

Give a fresh context the judge packet and the Judge inputs in diagnosis-cases.md. All verdicts and their reasons must return. The packet has source descriptions as checked premises; this tests judgment, not whether an investigator actually researched them.

- **J1:** push back. A cause fix is not the only useful response. Official failure semantics, the active provider chain and existing field semantics remain available for static investigation. An observable recurrence trigger does not explain how the next identical row would resolve attribution. Permit a bounded investigation before choosing implementation.
- **J2:** push back. Adding fields can be useful, but the promised complete edge-versus-origin discrimination contradicts the documented generic result and the proposal's own contrary evidence. A request ID alone does not attribute a cause. Require a narrower claim and residual evidence route, not proof of the historical cause before any improvement.
- **J3:** accept. Documented alternatives, bounded field value, delivered evidence, residual ambiguity, cost and next action are explicit. Neither a contract violation nor full historical attribution is required to justify this evidence improvement. Do not demand enabling every origin facility now.
- **J4:** accept. Verified accepted handling already answers the decision; the checklist must not force new research or work.
- **J5, redundant test:** push back. Known already settled by static review the fact the committed fixture test would establish, so the test changes no decision, and the outstanding recovery question (did that client converge and stay usable, what would show it) was not asked. Accepting the test as the committed operation fails. Pushing back merely because the proposal predicts the test's result also fails; the defect is redundancy and the unasked question.
- **J6, falsifiable validation:** accept. The same incident with a checked mechanism in Known, a fix now, a fixture test that fails before the repair and passes after it, this client's usable convergence observed in retained rows rather than inferred from a missing timeout, and the forwarded signal that shows the defective path. The predicted pass does not make the test redundant: it validates the repair and can fail. A judge that rejects it as a known-result check, or that treats the retained activity rows as insufficient recovery evidence, fails.
- **J7, known cause, fix only:** push back. The null dereference is a checked mechanism and the repair stands. The push-back is for the concerns marked inapplicable because the cause is known: the finance import silently reading a stale file needs recovery, feedback or an explicit owner policy, and the Error without an order identifier needs an evidence decision or a reason. Demanding retry redesign, a scheduler change or a device reproduction overreaches.
- **J8, known cause, secondary obligations met:** accept. The repair, the consumer-visible failure outcome, the order identifier in the Error, the owner's policy choice on alerting, and a bounded check with finance that decides whether the three missed nights need a replay are each stated with benefit, cost and validation; the proposal does not claim the fix restores the missed data. Do not demand further alternatives be excluded before accepting the mitigation; mitigation selects on supported benefit, not on an unresolved cause. A judge that pushes back for the historical recovery when that bounded check is committed fails.

Also run the existing outcome controls O4, O8, O9 and O10 in proposal-outcome-cases.md. All remain acceptable: sparse but adequate evidence, accepted recovery, a deterministic local cause repair with brief inapplicability bases, and harmless recomputation need no new provider taxonomy or instrumentation. O9's checked writer/reader mismatch establishes a supported operation's system contract; demanding a new owner document for routine safe loading is overreach. Judge the proposed fallback by its supported outcome and stated risk.

Compare reasons, not just verdicts. A verdict with the expected label and a reason that would also fit the paired case (J5 against J6, J7 against J8) fails that pair.
