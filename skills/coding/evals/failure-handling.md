# Failure handling checks

Read when maintaining cause selection, shared failure ownership, or user-outcome verification. Give fresh readers the candidate skill and scenario facts without the expected decisions below. Use isolated fixtures; no live project changes are needed.

| Case | Scenario | Expected behavior |
|---|---|---|
| Original: unresolved field crashes | A deep crash review finds several recurring client failures. One mechanism is proven, while the others lack the object identity, prior state, or third-party detail needed for a causal fix. The first report labels most groups "insufficient evidence; no change." | For every material group, identify the affected boundary and who can change it, then examine direct repair, containment, and bounded observability seams. A probe names its exact signal, insertion point, consumer, decision changed by each result, risk, and validation route. Leave a group intentionally unchanged only after explaining why none of those bounded options improves the user outcome or next decision. Do not present a probe as a fix. |
| Original: owned input failure | A creation dialog marks itself initialized before asynchronous data arrives. Commit accepts the current empty value. Its caller logs and rejects the value. The user asks to fix creation. | Trace the producer and commit timing, fix acceptance before dispatch, and check that empty input creates nothing while populated input still works. Additional logging alone fails. |
| Original: repeated failure handling | Several saves independently classify the same storage failure and show the same warning. A common write operation covers some paths; a library writer bypasses it. The user asks to simplify handling. | Compare the common operation and its actual coverage before adding more caller policy. Choose shared ownership where the facts and control meet, account for bypasses, and preserve distinct action completion or rollback. A shared helper that still leaves identical notification decisions in every caller is insufficient. |
| Original: required startup prerequisite | Startup catches initialization failure, logs it, and continues into an unusable screen. The external resource cannot be repaired by the application. The user asks to fix startup behavior. | Stop dependent startup and provide the required usable failure outcome. Verify the visible result and terminal action, not only the error signal or absence of duplicate logs. Do not invent a repair for the external resource. |
| Unseen sibling | Two account screens each retry and announce expired credentials. Their shared session client sees the same failure; a background sync also uses it. The user asks to fix repeated prompts. | Inspect common ownership and all three consumers, centralize the shared session decision, and preserve each action's success or failure contract. Verify that concurrent failures produce the intended prompt and no false successful action. |
| Unseen sibling: unknown corruption source | A background import sometimes produces corrupt output, but the retained report has only the final parse failure and cannot identify which producer wrote the bytes. | Do not stop at the missing writer. Inspect whether atomic output, validation before publication, producer identity, or a retained input/output digest can contain the failure or distinguish producers. Recommend only signals that select a different repair; if no owned seam can do so, explain that boundary specifically. |
| Near negative | The user requests only a diagnostic wording change, explicitly preserving behavior. The failure comes from a third party. | Make the wording change and verify it without redesigning recovery, auditing unrelated producers, or broadening the request. |
| Known-good | A common operation already reports failure accurately, one UI owner handles it, and callers preserve their distinct outcomes. The defect is one missing subscription. | Repair the subscription and verify the actual user outcome. Do not replace the working ownership model or perform an open-ended design search. |

Report observed decisions and execution separately. A scenario response checks judgment; an executed fixture checks whether the selected fix works. Neither establishes behavior in an unexecuted product workload.
