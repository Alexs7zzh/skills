# Independence, the deep run

A second reader who did not form the conclusion, and how two verdicts reconcile. Read when the user asked for a deep run, a review touches a risk surface, or a master dispatched you as a peer in a two-family run. Choose your role first; the Herdr wiring is the last section. A subagent inside a single session is not a peer and does not need this file.

Cross-examination converts confident false cleans, and confident false dismissals, into findings; convergence-gating alone would discard exactly the disputed items. That is why a contested item escalates to a probe instead of being dropped. Reasoning is shared in cross-examination because it is the thing under attack; the fresh attack and the fix review withhold it because independence is the point there.

## Rigor by label

Bug and Restructure rows get the full protocol: cross-examination, fix review, the proposal slots, and probes. Composition rows are cross-examined like Bug rows and carry no proposal slots. Hardening, Nit, and telemetry-quality rows close in one line with their disposition, or are carried as written, and never open a cross-edit. None of the reversals that matter come from a low-severity row, so the budget goes where the label says.

## The deep run

The work is the route's procedure: review.md or diagnose.md, plus the project's own doc. Deep adds these steps around it.

1. **Fan-out floor.** Coverage is an attention problem: a reviewer who follows only the suspicious parts can dig deeply and still miss a blocker in an ordinary hunk. Every lens the change touches runs as its own pass; every changed hunk sits in exactly one sweep's scope; the sweeps together cover every object under Enumerate in good-code.md; in a diagnosis, every cluster has its own investigator. Sweeps are mechanical and belong to cheap agents, one per area, reading every hunk line by line and returning obligation rows, file:line plus the claim, and anything odd. Lens passes, cluster investigations, verdicts, composition and the adversarial pass belong to strong models; enumeration, sweeps and probe running to cheap agents. Dispatch sweeps and passes together and let their results meet in the ledger; in Claude Code, dispatch them as one workflow, each returning rows. Start the mechanical sweep first as the long pole, and never finalize with passes outstanding; if time runs out, name each unreturned pass and the code it leaves unenumerated as an honest gap.
2. **Close the ledger.** The ledger is a SQLite file driven by `ledger.sh`, which sits beside this file; `ledger.sh --help` lists its commands. Every protocol fact lives in it: the rows and their marks, which seat is the scribe, the joint report path, the partition, the imports, and the countersignature. Every notification is sent by the helper from a state change and names the receiver's next command, and every mutating command prints the unconverged count and your next step, so the protocol is read from the ledger rather than remembered:
   - One row per claim: label, the clusters it dispositions, claim, certainty step, evidence path, status, and the slots its label needs. Every row ends in a state from findings.md.
   - One convergence rule for every row, contested included: a row converges when the peer who did not last edit it marks it with `agree`. On a contested row the mark agrees that the named probe settles it. Writing is standing by your text, so you never mark your own edit, and after a cross-edit the mark that converges the row is the author's.
   - Every content edit goes through `set`, which advances the row's revision, clears both marks, and voids any countersignature; a raw edit aborts. Rows are withdrawn, never deleted.
   - `verified` needs step 4 and an evidence path; `contested` needs a probe; a Bug or Restructure cannot converge with an empty trigger, impact, cost, or proposal slot, and its test seam states `exists: <path>`, `new: <what must be built>`, or `none: <the architecture finding>`, so a described test is never mistaken for a runnable one. After two cross-edits that leave a row below step 4, the next edit must contest it with a probe or land step-4 evidence.
   - Coverage is checked against the partition: `status` and the render name every cluster no row dispositions, and `converge` refuses while one is uncovered. A row names every cluster it covers in its cluster field, so a row per cluster is not needed.
   - `review <id>` records the countersigner's fix review of a proposal at its revision; a later edit needs a new review. A proposal is ready for a fixer when it is converged and reviewed, and `status` lists the ready rows.
   - `sign` is refused, by the schema in one statement, while any row is unconverged, any proposal is unreviewed at its revision, or a seat has no Composition row. It records the hash of the seat notes, and `converge` refuses if they changed.
   A single-session run, plain or deep, uses `init --single` and `report` in place of imports, marks, and signature: the slot and coverage checks then run at `report`.
3. **Compose.** When the factual rows have converged, each seat composes independently, before reading the other's composition. Deduplicate to root causes. Re-verify the top finding in code before accepting it, and list every dropped or downgraded finding with its reason. Then read the findings as a set rather than a list: for each pair on the same user path, ask what holds when both are true at once. Two individually reasonable decisions compose into the severe finding, since a defense removed here plus its replacement inert there is a regression rather than two inert features, and severity, ordering and fix sequencing all shift under composition. Write the result as Composition rows: the row ids composed in the cluster field, what the set means for one user on one path as the claim, the fix order or changed severity as the decision; or one row saying nothing composes. Then `handoff`, and the compositions are cross-examined like any row. A new fact found while composing is a new row, which reopens convergence by itself. Compose yourself, with the whole set in view.
4. **Fresh attack.** Hand the composed set to a fresh strong model: findings, composed severities, and clean rows in both directions. Fresh eyes means a fresh context, not a re-read by whoever formed the conclusions. The attack re-verifies every finding, and re-examines clean and assumed rows wherever a blocker could hide.
5. **Fix review.** Hand each release-gating proposal, as a diff without the reasoning that produced it, to a fresh strong model to review as a change. The fix review walks the code; any execution routes through the validation owner.
6. **Report** per the route, with a `passes:` line per reviewer: `passes: N sweeps, N lenses, N probes, N fix reviews`, naming every pass that did not run.

## Two families

Two frontier reviewers from different model families run the work independently, cross-examine each other directly, and converge peer-to-peer. The master is the user's window. In a two-family run the peers skip step 4 of the deep run, since cross-examination is the fresh attack; step 3 runs as Composition rows once the factual rows converge; and step 5 runs row by row, by the countersigner, recorded with `review`. Choose your role once, before reading any steps, and follow only its section.

| You are | Role |
|---|---|
| The user-facing session, and the Herdr preflight below passes | **Master** |
| The user-facing session, and the preflight fails | **Local reviewer.** Say the runtime is unavailable, then run the deep run in this session with subagents, owning validation yourself: build once and run the owning suite. Never imitate the peer exchange without the runtime. |
| An agent dispatched by a master | **Peer.** Run the work and follow Peers below. `ledger.sh status` tells you whether you are the scribe or the countersigner. Never wire or manage the run. |

### Master

Never perform the work, merge findings, or relay reviewer traffic. Never pre-study the items; read project rulings only when gating. Read this file and the project's route doc for its gathering steps, and nothing else: the peers judge.

- **Gather.** Run the route's gathering steps, the ones that produce the input and its partition without judging any item: for a review, the changeset inventory; for a telemetry triage, the export, grouping, cluster list and the input's hash; for a crash-report sweep, the issue list and the event-history dedup into incidents. Run the route's standard probes at freeze time, the ones any peer will ask for, and put their results in the frozen input; the project's route doc lists them. Freeze the result in the run directory and create the shared ledger there: `ledger.sh init --scribe <A|B> --joint <joint report path> --route <review|diagnose> --clusters "<the partition's ids>"`. Both peers receive the identical partition, and the dispatch names it.
- **Own validation.** Build once, run the owning suite, and run the probes both peers queue, serialized, writing logs to the run directory. Peers close validation from those artifacts at step 4 rather than racing a second editor instance. You are the one editor of temporary changes.
- **Wire and dispatch** per the Herdr section, naming a wall-clock budget: reports due forty minutes after dispatch, convergence twenty minutes after that. A peer at budget freezes what it has, names each unreturned pass, and carries open items as contested. Round 1 is cold: no peer contact until each report is done.
- **Gate, then stop.**
  - Gate only on the scribe's `converged:`, which the helper sends only when the ledger is at zero and countersigned. `signed:` alone is not a final report, and peer traffic that reaches you before `converged:` is information and never a reason to gate or present. After a bounce, gate again on the next `converged:`.
  - Check `ledger.sh status` for uncovered clusters, then the joint report for: the line bound below; decision packages a non-expert owner can decide from; contested items carried with probes, each contested fix shape carrying its axis; every section the route's report mandates, including a Trigger on every finding, a `passes:` line per reviewer, and the fix table or dispositions; for a diagnosis, every cluster dispositioned, every cause with its step, every proposed fix with its slots or marked a direction; and the countersignature.
  - Bounce it back to the pair once if anything is missing. Gate large reports by section grep plus targeted reads, because a full dump truncates.
  - State the verdict as one line: `sections: <present> | uncovered clusters: none | countersignature: <who>`.
  - Present the report in the route's shape, plus the convergence map of agreed, withdrawn and contested-with-probes items, both retrospectives, and what each round's fixes changed. Then stop. Fixes and any next round start only on the user's go, and the user may amend the fix list, rule on contested items, or stop the loop.
- **On go: fix and validate.** Dispatch ready rows as `status` lists them: a row is ready when it is converged and fix-reviewed at its revision, and a ready slice starts without waiting for the signature over the rest. Every approved row is in scope, rulings are stated by their option label, and the fixer does not stop to ask between rows. The scribe closes each landed row with `set <id> status=fixed changeset=<id, or pending: summary until checked in>`, and the other seat marks it like any edit. The fixer checks each claim it builds on against the current revision, since a link error or a failing falsifier is a fact. Fixes go in batches of independent rows per Permissions, with a flaky test folded into the next full run. A hot round goes to the same reviewer sessions, since their context is the point; spawn fresh sessions only for a cold full re-review. Cap at 3 rounds.

### Peers

- Run the work independently first, in your own cold ledger (`ledger.sh init --cold`), with no peer contact until `ledger.sh import` moves your rows into the shared ledger and tells your peer; that import is your report. Your `passes:` line, retrospective and vote go in `<seat>-notes.md` in the run directory; `converge` appends both seats' notes to the joint report. Ending your turn after a notification is for when you are still waiting on the peer: if the peer's rows are already in when yours land, continue straight into cross-examination in the same turn.
- **Cross-examine** from the queue `ledger.sh status` shows, row by row, the moment both imports are in. For every row you did not last edit: `agree`, `reject` with evidence at certainty step 2 or better, `contest` naming the probe that would settle it, `set` a correction, or `dup` it onto the row it restates. Fan the examination out with subagents, one per claim cluster, each returning its verdict with evidence, and delegate any probe whose output is bulk; queue probe runs to the validation owner so they batch with builds already running, and take the write-up with `claim-probe`. Work the queue until it is empty, then end the pass with `ledger.sh handoff`, which tells your peer what awaits them; a pass that ends without `handoff` stalls the round. A row you edited returns to your peer's queue, since the mark that converges it is theirs. Yielding without a certainty-step citation is not agreement: contest.
- **Amendments** are row edits: each names the corrected value or state and its certainty step in the row itself, never in a message or a line number. The schema ends the argument after two cross-edits; whatever remains is a contested row with its probe.
- **Closing a round.** At unconverged zero each seat writes its Composition rows and hands off. The countersigner then runs the fix review, step 5, row by row on the open proposals as diffs without the reasoning that produced them: applied as temporary changes through the validation owner and built where the build is affordable, walked at every site otherwise. It checks each seam claim against the code, since `exists:` is a path to open, writes its conditions into the row with `set`, and records `review <id>`, with the note saying whether the proposal was applied or walked; the scribe re-marks edited rows, and an edited row needs a new review. The fix review keeps to the budget like every pass: at the budget, an unresolved point becomes a condition in the row rather than open time. With every row converged, every proposal reviewed, and both compositions in, the countersigner runs `ledger.sh sign`, which records the countersignature and the seat notes' hash and tells the scribe and the master. Any edit or new row after that voids the signature, so nothing is edited after `signed:`. The scribe then runs `ledger.sh converge`, which refuses an uncovered cluster or changed notes, renders the joint report, appends both seats' notes, and tells the master. Neither seat types `signed:` or `converged:`; the helper sends them. If your peer is silent for 30 minutes, notify the master.

### Scribe only

- Before `converge`, read `ledger.sh render` against the master's gate list, and escalate anything that needs a user ruling immediately, rather than at convergence.
- The report is the render plus the two notes files: author no claim into it that has no row, and keep the whole under 300 lines by leaving the incident roster, verified-clean entries, and evidence in files referenced by path, since free-form prose drops the slots the template exists to force. A correction is one row edit; the countersigner then re-marks and re-signs.
- After the master's gate, nothing is filed: the rows leave the ledger through the exits in findings.md as the fixes land.

## Herdr runtime

Wiring for a two-family run. Read when you are the master of a deep run or were dispatched into one. The method is above; `herdr <command> --help` answers flags.

**Preflight.** `test "${HERDR_ENV:-}" = 1` and a responding `herdr agent` command. Either failing makes the user-facing session the local reviewer.

**Cast.** Reviewer A is Claude Opus at high effort, ledger seat A, and is the scribe by default; the master may give the scribe role to either peer. Reviewer B is Codex `gpt-5.6-sol` at high effort, ledger seat B. Each runs the work with its own subagents.

**Layout.** One new tab for the run, named short after the target ("review cs 15944" or "triage 2026-09-02"). One pane per reviewer, side by side rather than stacked, each named after its agent ("opus-reviewer", "codex-reviewer"). Rename your own agent to an addressable name first with `herdr agent rename`, since reviewers message you by that name. Start each with `herdr agent start <name> --kind claude|codex --pane <pane-id>`. Parse ids from JSON responses rather than guessing, and use `--no-focus`.

**Run directory.** The frozen input, the ledger and its cold ledgers, the joint report, the seat notes, and validation logs travel as files in one run directory, created fresh per run and named after the kind and the time, under the project's ignored in-project folder when its review doc names one, otherwise under a temporary directory. If a directory for this run already exists, archive or wipe it, and stop any prior attempt's agents before dispatching new ones, because leftovers masquerade as this run's evidence. `init` copies the helper and its schema into `<run dir>/bin/`, and every later command runs that pinned copy whichever copy was invoked, so a run never sees a helper change. Past run directories are not inputs: no step reads them, and no agent removes them.

**Dispatch.** Carry only what is unique to this run, and point the peer at this skill by name, which is what makes it loadable in the peer's agent:

```
Deep <review|diagnosis> of <target>. You are <name>, a peer in a deep run; read the `coding` skill (`$coding`), then deep.md, and follow the Peers role. Frozen input: <path>. Ledger: `export LEDGER_DIR=<run directory> LEDGER_ME=<A|B> LEDGER_PEER=<peer agent name> LEDGER_MASTER=<your agent name>`. Budget: report by <time>, convergence by <time>.
```

The scribe seat, the joint report path, and the partition are already in the ledger from `init`, and `ledger.sh status` tells each peer its role. Append constraints the user stated, verbatim, and invent none. Do not restate protocol steps and name no notification strings; this file and the helper carry them. A sentence you repeat every run is a missing doc line, so move it.

**Messaging.** `ledger.sh` sends the four notifications through `herdr agent prompt`, using `LEDGER_PEER` and `LEDGER_MASTER`: `report ready:` on import, `ledger:` on handoff, `signed:` on sign, `converged:` on converge. Each names the receiver's next command. If delivery fails, the helper prints the message: send it yourself, or finish and let the panes be the fallback read. After any notification, end your turn, because replies arrive as prompts.

**Waiting.** Never wait on review work: no `--wait`, no polling, no pane peeking, no progress narration. Dispatch, go idle, resume on notification. The rule binds peers too: never `herdr agent wait` on your peer or pump its stdin; `ledger.sh status` between rows is a local query, not a wait. `--wait` with a tight timeout is fine for short control exchanges. One liveness exception: when a prompt reaches you after `signed:` and `converged:` still has not, ask the scribe for `ledger.sh converge`, one control message rather than polling, because a dropped notification must never strand a finished report.

**States and cleanup.** Agent states are `idle`, `done`, `blocked` (surface to the user), and `unknown`. Close only panes you created, and never stop the Herdr server.
