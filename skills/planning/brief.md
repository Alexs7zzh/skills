# Brief

Synthesize the established conversation and relevant code or task evidence. Do not start another interview or invent requirements to fill a template. If context is insufficient for a claim, label the gap and its consequence.

Write only the sections with meaningful content:

- **Outcome and scope.** The user problem, intended experience, and explicit exclusions.
- **Human rulings.** Decisions with their sources and reasons when given. Link maintained rulings instead of copying a competing version.
- **Acceptance.** Scenarios that distinguish the desired result, including consequential failure behavior. Do not generate an exhaustive story list by expanding every noun into a feature.
- **Current evidence and proposed approach.** What is established, what remains unverified, and any provisional design needed to continue. Include a code shape only when it expresses a decision more precisely than prose; identify its status.
- **Open questions and dependencies.** What remains undecided and which work it affects. Omit empty categories.

Keep implementation detail to what the next reader needs to act or assess a choice. Link supporting investigation rather than embedding the whole analysis. The brief is working material under the shared retention rules.

Write to the requested destination. If issues are requested, the map method can use the discussion directly; do not manufacture a separate spec as an intermediate deliverable.
