# Constraint model: directory cache subsystem

## Orientation

**Target and revision.** The listing directory module at `/tmp/ca-trial/20261007-1316/fixtures/cache-ttl-review/`, namespace `Social.Directory`. The snapshot has no version control, so every row is pinned by file content hash (SHA-256, first 8 hex digits shown in Sources; full hashes in Appendix A). Access was read-only file reading. No build, run or measurement was performed. Inspected: `goals.md@ed0b1735`, `src/Caching.cs@ff26d320`, `src/DirectoryModule.cs@711152d5`, `src/Listings.cs@3faeddd0`, `src/Subscription.cs@5230bd9c`, `src/Presentation.cs@20a9f752`. No project file, target framework, package list or project instructions exist in the snapshot, so the .NET and C# versions are not pinned.

**Purpose.** The module keeps two main-thread caches of directory listings: the room list (`Rooms`) and the favorites list (`Favorites`). A background refresh loop fetches the full directory from the service, a push subscription removes rooms the host closed, and a frame-driven dispatcher applies both to the caches on the main thread.

**Governing constraints (goals.md, authority: client platform goals of 2026-01 and directory service contract v1).** Current obligations:
- G1. The room list shows only listings the service still considers valid. Validity is `TtlSeconds`, counted from the moment the service produced the response. The client may show a listing for a shorter time, not a longer one.
- G2. A room closed by its host leaves the room list and the favorites list within 1 second of the `rooms.closed` push event, without waiting for a refresh.
- G3. Directory requests are bounded so a hung service never blocks the refresh loop indefinitely. No requirement sets the magnitude; service response times on client networks are unmeasured.
- G4. Room-list lookup hits and misses go to telemetry. Favorites store mutations are logged at Debug.
- G5. `BeginShutdown` runs on the frame the session ends; `CompleteShutdown` runs after the final dispatcher drain, at most two frames later. After `BeginShutdown` the directory must not act on push events.

Accepted tradeoffs: A1, the dispatcher drains once per frame and frames stop while backgrounded, so queued work can run minutes later. A2, a refresh failure (timeout or transport error) skips that cycle. A3, a page reflects service state when the service produced it, so a room closed while a request is in flight can reappear when that page is applied and leave on the next refresh. A4, rooms and favorites are separate stores so their decorators can differ. A5, push callbacks run on the channel's thread and may be delivered until the handle is disposed; per the provider, disposing the handle blocks until no callback is executing.

Non-goals: persisting listings across launches; revalidating a single room on lookup.

No historical proposals were supplied. Code comments are source intent, not obligations; where a comment and the code differ, both are recorded. Two pairs of supplied rules touch the same fact and are kept as given, unreconciled: G1 (never show longer than service validity) with A1 (queued work may run minutes late), and G2 (a closed room leaves within 1 s) with A3 (a closed room may reappear from an in-flight page).

**Boundary.** The subsystem is bounded by the producers of cache contents and their removal: the HTTP directory client, the refresh loop, the main-thread dispatcher, the two expiry caches and their store decorator chains, the push subscription, and the module's composition and two-step shutdown. Excluded, and consequential because they decide rows left unresolved:
- The composition root and frame loop (outside the snapshot): which `TimeProvider` and `HttpClient` (BaseAddress, `Timeout`) are passed in, which synchronization context `RunAsync` is started from, who observes the `RunAsync` task, and where `Drain` runs within a frame relative to `BeginShutdown`.
- Cache readers (outside the snapshot): callers of `TryGet` and `Live`, and how long they hold `Live()` results.
- Implementations of the push channel, favorite membership (`IFavoriteRooms`), metrics and logger. There is no path in the snapshot for favorite membership changes (for example unfavoriting) to reach the favorites cache; the request does not cover that path.
- The directory service contract v1 itself; only the goals' summary of it was available.
- Presentation (`RoomNameFormatter`, `DirectorySort`): inspected, does not produce or remove cache contents, and has no caller in the snapshot.
- Diagnostics lens: not selected for this run; logging and metric calls appear only as wrapper capabilities.

**Ordinary path.** A composition root constructs the module with an HTTP client, a push channel, the favorite-membership source, a metrics sink, a logger and a clock. The constructor builds the room list as an expiry view over a lookup-metering decorator over an in-memory store, and the favorites list as an expiry view over a mutation-logging decorator over a second in-memory store; it builds the refresh loop and the push subscription, which subscribes to `rooms.closed` immediately. When the caller starts `RunAsync`, the loop fetches `/v1/rooms` at once under an 8-second bound and posts a closure to the dispatcher. On the next frame the main thread drains the queue: the closure replaces the whole room store with the page and the whole favorites store with the page filtered by current favorite membership, stamping each entry's expiry as the clock's now at drain plus the listing's `TtlSeconds`. The loop repeats on a 60-second timer. Readers ask a cache for one room or for all live rooms; both compare stored expiry with the clock's now. A `rooms.closed` event on the channel thread posts a closure that, at the next drain, asks both caches to remove the room. At session end `BeginShutdown` cancels the refresh token and retires the subscription; after the final drain `CompleteShutdown` disposes the push handle and the cancellation source.

**Evidence legend.** **S** source-established: expressed in the snapshot's code, not confirmed at runtime. **P** provider contract: .NET/C# platform behavior (the snapshot pins no framework version) or a provider guarantee stated in goals.md. **M** measured: none in this model. **U** unresolved: the missing fact is named.
