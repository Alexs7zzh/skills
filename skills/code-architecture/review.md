# Review the account and develop remedies

Use this stage when the user requests architecture review. Read the target project's review instructions and applicable coding judgment guidance. Retain the research revision, goals, accepted tradeoffs and evidence limits. A later baseline change requires checking affected facts, not discarding the account.

## Independent judgments

Unless the user selects another arrangement, give one fresh reviewer the complete account and separate fresh reviewers the orientation plus each selected applicable principle section. Each reviewer also receives the principle definitions, goals/rulings and this review contract. Honor role-specific model/effort choices. Do not give reviewers peer results, prior verdicts or a preferred replacement design.

Use available worker slots for substantive reviews. The coordinating agent can consolidate completed work while other reviewers run; do not dedicate a worker merely to wait or schedule. If the limit requires batches, record that constraint without attributing the elapsed batching time to model quality. An execution limit does not permit silently reusing one reviewer for a requested set of independent reviewers; disclose the reduced independence if the requested arrangement cannot be completed.

**Trust the research's factual account.** Read another section when the question crosses its boundary. Consult retained source or return a focused question to research only when a material missing fact or contradiction changes the judgment or remedy. Record the specific gap and the answer; do not rerun source inventories, hash checks or routine verification. If the account is wrong or insufficient, identify that research failure instead of silently making every reviewer rebuild it.

Each reviewer returns:

- **Assessment:** the selected rule or rules, supported concern or no supported concern, factual basis, and the scope/limits of that conclusion. A missing fact is not a clean bill or automatically a defect.
- **Concerns:** for each, the required outcome or concrete maintenance task, causal mechanism, affected consumer, evidence, counterevidence and confidence. Distinguish a local mistake from a structural cause; both may contribute.
- **Remedy direction:** a local correction and, where the failure class warrants it, the smallest structural alternative. Name the existing owner or abstraction and the invariant it would enforce. Explain why the recommended choice earns its cost; do not prescribe RAII, a type, a new layer or a rewrite merely because it is familiar.
- **Gaps and checks:** material facts still missing, extra reads and their purpose, and checks actually performed. Separate inspected code from executed behavior.

Stop within the selected question's scope. Preserve accepted tradeoffs and unknown provider guarantees. Do not invent a finding to fill a rule or treat an unmeasured policy constant as a proven incorrect value.

For principle 33, judge the coverage map, diagnostic state and policy-to-output tables against the logging and outcome contracts. Check required evidence at its destination, classification precedence across admitted provider levels, preserved causal distinctions, later episode enrichment, event identity/coherence and recurrence after recovery. An excluded producer is a coverage limit, not a clean result. Separate an external incident from an owned classification, retention or handling defect. Missing native cause or original severity limits incident attribution; it does not erase a source-established policy violation. Recommend additional logging only for a consequential question the existing evidence cannot answer.

## Synthesize once

Merge findings by causal mechanism and affected contract, not by rule number or similar titles. Preserve distinct facets and their source, including a cross-boundary concern that only the whole reviewer saw. Keep correctness, concrete maintenance costs and unresolved evidence gaps distinct. Resolve material disagreements with the existing facts or a bounded lookup; peer agreement alone does not prove the claim.

For each retained concern, produce one implementation handoff with:

1. **Outcome and cause:** what breaks or becomes hard to maintain, under which trigger, and whether the cause is a local omission, a structural contract weakness or both.
2. **Selected remedy:** choose the smallest sufficient design, name its owner and explain the alternative rejected. If the choice depends on missing evidence or a user tradeoff, state that exact dependency instead of presenting several unranked options.
3. **Patch boundary:** affected producers, wrappers, consumers and relevant initial/refresh/replacement/teardown siblings. Preserve existing behavior outside the correction. Do not turn this into a repository-wide sweep.
4. **Verification:** a test or code argument that distinguishes the defect from the correction, including meaningful timing or lifecycle boundaries. Name existing seams where known. A behavior-preserving extraction may need only a build and diff review; comments do not require new tests.
5. **Readiness:** ready to implement, a named design/evidence decision remains, or no code change is justified. State the missing step. A fix direction is not a completed patch, and a proposed test is not execution evidence.

One synthesis owns this handoff; every reviewer need not design a competing patch or repeat the source investigation. Keep the final result concise and link detailed evidence. Where timing or cost is requested, distinguish wall time, scheduling and model execution; disclose procedure changes and unavailable token/cost data.

## Authorized implementation

Research or review alone does not authorize project edits. When the user also asks for fixes, use the handoff in the normal project coding workflow: check the current baseline, make recoverable scoped changes, run required builds and discriminating checks, and report what actually passed. Preserve unresolved evidence gaps rather than making speculative changes to close every review row. Do not repeat the architecture review merely to start implementation.
