# Compare and synthesize

If the target moves to a new revision before compare, the coordinator re-checks the model rows whose sources changed and records the new revision in the orientation.

## Comparers

Unless the user selects another arrangement, run one whole-model comparer and one focused comparer per section group that has a K row or a design encoding touching it. The groups are listed under Terms in SKILL.md. Merge two groups into one comparer when neither has a K row of its own.

Every comparer receives the path to the full model, the design, the goals and rulings, the project's review instructions, [lenses.md](lenses.md) and this contract. The whole-model comparer reads the whole model. Its design check covers every encoding named anywhere under the design's Conflicts resolved section, and any encoding no focused comparer owns; the focused comparers own the rest. Its divergence rows are the cross-group ones, and it adds `## K row coverage`: one line per K row naming the encoding that answers it, or `unanswered`. A focused comparer reads the orientation, its group's sections and the collapses and overlaps, and looks up any other row an encoding or divergence cites; it does not read the whole model. A focused comparer's assignment is its section group; it writes full rows for those sections and gives a mechanism whose home is another group one line naming it and the group, so synthesis merges once. No comparer receives peer results, the design agent's reasoning or a prior verdict. If a slot limit forces batches, record it. Do not reuse one comparer for a requested set of independent comparers without disclosing the reduced independence.

**Trust the model.** Open retained project source, or send a focused question back to extraction, only when a missing fact or a contradiction changes a judgment. Record the gap and its answer. Provider documentation of the matching version, and the provider implementation the build selects, are not project source. Read them when an encoding rests on provider behavior the model does not record. The contracts comparer owns those reads; the whole-model comparer owns them when that group does not run. Another comparer gives such an encoding one line that names the provider claim and that group, so each provider fact is read once. If the model is wrong or insufficient, name that extraction failure. Do not rebuild the model in every comparer.

Before judging the code against an encoding, judge the encoding. It is a **design defect** when its form or level is wrong: anything it states or implies, including a numbered premise, is refuted by the model, by the provider implementation the build selects, or by version-matched provider documentation, so the form cannot enforce the invariant; it matches a shape in [Checking a design](lenses.md#checking-a-design); another part of the design already makes it unnecessary; or it names no form concrete enough to refute, the invariant restated as enforcement. A level claimed that the form does not reach, a gate that can only observe, is a defect under that shape even when the form is concrete. When the form and level stand and only a stated bound, cost, lag, count or wording is wrong, the row is a **correction**, not a defect. The current code avoiding the bug does not pass the encoding; judge the encoding as written.

Judge each encoding by four sweeps, not by reading it once:

1. **Routines.** For each provider routine in its Replaces and Performs slots, find the model's `PR` row, or read the provider implementation when there is none and record that read. A routine the encoding calls whose `PR` row writes a root the encoding claims to own is a defect.
2. **Writers.** For each root the encoding claims one writer for, or refuses writes to, list every writer the model records for that root: the subsystem's own rows and the `PR` rows. A writer the encoding neither refuses nor routes is a defect.
3. **Level.** Place the refusal relative to the write, by the gate definition in SKILL.md's Terms. A level claimed above what the form reaches is a defect.
4. **Shapes.** Run the list in Checking a design.

Each comparer's output opens with `## Design check`: a table with one row per encoding in its sections, columns id, result (`passes`, `correction`, `defect`), tested against (the `PR`, `S`, `O` and other row ids and the provider reads the sweeps touched), lens slug, note. A correction's note is the corrected statement; a defect's note is the shape or the row, provider code or document that refutes it. The code is not judged against a defective encoding; it is judged against a corrected one.

Then `## Divergences`: one `### E<n>` entry per remaining design encoding in its sections. An entry is "matches" with the rows that show it, or "not checkable from the model" with the missing fact named, or these slots, each on its own line:

- **Divergence:** the design's encoding, the model's recorded enforcement, and the lens slug.
- **Bug class permitted:** what can be written under the current form that the design forbids, as a concrete sequence: this state, this action, this event, this outcome.
- **Instance:** a model row showing the bug class realized, or "no instance in evidence".
- **Consequence:** one of `ruling`, `user-visible`, `leak`, `diagnostic` or `none`, the first that applies in that order, then who meets the outcome and what they see, on the model's facts. `ruling` names the `O` row violated.
- **Disposition:** one of five. Finding: the bug class is reachable on the model's facts, with or without an instance. Conditional finding: reachable only if a named fact about the environment goes one way: content, configuration, a provider mode, a platform. Justified tradeoff: the ruling or constraint that justifies it. Not a finding: the code differs from the design but the model shows the combination excluded another way. Evidence gap: a fact about the code or the provider that the model should record is missing, so the comparer cannot say whether the code diverges.
- **Confidence and limits:** what would change the disposition.

For the diagnostics lens, follow the compare cues in [logging.md](logging.md). Before returning, run `python3 scripts/check_artifacts.py compare <file> --design <design.md>` and fix what it reports.

## Revise once

If any comparer returned a design defect, a fresh designer revises the affected encodings once, with the defect rows added; corrections go to the synthesizer, not the designer. `design-revised.md` is the whole design, and each encoding heading carries `Revised`, `Unchanged` or `New`. A fresh comparer for each section group the revised or new encodings touch, and the whole-model comparer when a new encoding touches more than one group, then runs the design check and divergence rows on those encodings only. There is no second revision: second-round defects, corrections and divergences go to synthesis, which answers each defect inside the handoff it affects, choosing the form and giving that choice the design check. A defect on an encoding whose divergence is a lower row is answered in that row's line; it does not raise the row to a handoff. Run `python3 scripts/check_artifacts.py compare <file> --design design-revised.md` on a recompare file, since it covers the revised encodings only.

## Synthesize once

A fresh synthesizer receives the model, the revised design, the goals and every divergence list. A remedy the synthesizer introduces that no comparer saw gets the same design check before it enters a handoff. Merge rows by mechanism and affected contract, not by lens or title. Keep distinct facets and their source, including a cross-group divergence only the whole-model comparer saw. Resolve disagreements with the model or one bounded lookup; agreement between comparers proves nothing by itself.

**Consequence decides what becomes a handoff.** A merged row earns a handoff when two things hold. Its disposition is Finding, or Conditional finding whose deciding fact an `O` row states as the environment's normal case. And its consequence class qualifies: `ruling` and `user-visible` always; `leak` and `diagnostic` when an `O` row states a resource or monitoring obligation; `none` never. When the user supplied no goals, the orientation says so, and only `ruling` from project instructions and `user-visible` qualify. Every other row goes to one table, **Lower rows**: a row with consequence `none`, a conditional row resting on unread content, a correction, and a defect the revision already answered. A lower row is one line: the disposition, the lens, and the fact or decision that would promote it. A borderline row whose fix is free inside a structural handoff's migration rides there as a named facet in that handoff's patch boundary. It gets no handoff of its own. Work the goals require that no divergence produced, such as a planned deletion or a flag rollout, also goes into the patch boundary of the handoff it ships with. First-round rows on encodings the revision changed supply code facts only. The developer reads the handoffs. The lower rows are the record that lets the run stand without a repeat.

**Decisions and defaults.** A decision exists only when a handoff's Readiness depends on it; name the handoff. A choice that only a lower row needs goes in that row's promoting-fact cell. Ask a decision only when the options differ in scope, ownership or a ruling: widening to another role or process, changing a protocol, or a value the design offers no derivation for. A scope widening a handoff needs stays a decision even when the fact that makes it reachable is unread; name that fact. Where the design proposes a value with its basis, or a recommendation, and the alternative does not differ in scope, take it. List it under **Defaults taken**, one line each, so the developer can overturn it without being asked. When a section has nothing, write `None, because <reason>` under its heading.

The synthesis has these sections in this order: `## Summary`, `## Handoffs`, `## Decisions`, `## Defaults taken`, `## Lower rows`, `## Request coverage`, `## Ledger`. Request coverage is a table with one row per `O` row of the model: the handoff or lower row that answers it, or `none, because <reason>`. The Summary is at most 500 words: the target structure in one paragraph, the handoffs that change structure rather than patch a line, the decisions, and the counts of lower rows and defaults taken. A handoff is at most 600 words. The bound trims prose; it never splits one mechanism into two handoffs. Two rows with one mechanism and one patch boundary merge even when the merged handoff must be cut hard to fit. Write handoffs in the vocabulary of the model's Sources columns: files, routines and fields. Roles are the design's vocabulary, not the handoff's. Run `python3 scripts/check_artifacts.py synthesis <file> --model <model.md>` before returning.

For each retained finding, write one `### H<n>.` handoff with these six numbered slots, ordered by the consequence of the bug class:

1. **Outcome and cause.** The concrete sequence that breaks, and whether the cause is a missing encoding, a missing gate, or a local omission inside a sound structure.
2. **Remedy.** The structure that removes the bug class, named by its code form and owner, and the smallest migration that reaches it. If the user defers the migration, the local stopgap, labeled as a stopgap. Name the alternative rejected and why. If the choice depends on missing evidence or a user tradeoff, state that dependency instead of listing unranked options.
3. **Patch boundary.** Producers, wrappers, consumers and the initial, refresh, replacement and teardown siblings the migration touches. Preserve behavior outside the correction.
4. **Verification.** A check that fails under the current form and passes under the remedy: a type that no longer compiles the bad sequence, an assertion at the gate, or a test at the real wiring that runs the interrupting event. Name existing seams.
5. **Readiness.** Ready to implement, a named decision or fact outstanding, or no change justified. A direction is not a patch; a proposed test is not evidence.
6. **Lens.** The slug.

End with a **Ledger** table in the columns of `evals/lens-ledger.md`: one row per handoff, and one per defect that changed a form, merged by mechanism. Each row names its lens. Result stays blank until the user confirms or refutes it. Lower rows get no ledger row. Link the model and design for detail.

## Verify once

The ledger records findings that reached synthesis and were later refuted, and model statements the comparers found wrong. So each handoff's facts are checked once at the source before the developer reads them. For each handoff, a fresh verifier receives that handoff's text alone, the model's orientation for the revision and source aliases, the appendix excerpts for the rows the handoff cites, and read access to the project and the provider implementation at the pinned revision. It does not receive the design, the other handoffs or the comparers' lists, and it does not judge consequence or remedy. It checks facts:

- each step of the Outcome and cause sequence: the state, the action, the event, the outcome, each at a file and line;
- each routine the Remedy overrides or forks: it exists, and it is overridable (virtual, a hook, a delegate) where the remedy overrides it;
- each seam the Verification names: it exists and reaches what the handoff says.

It writes `verify-H<n>.md` with `## Steps`, a table of one row per checked item with its part (`Outcome`, `Remedy` or `Verification`) and `Confirmed <file:line>`, `Refuted <what the source shows, file:line>` or `Unverifiable <what is missing>`, and `## Verdict` with three lines, `Outcome:`, `Remedy:` and `Verification:`. A part is Refuted when the source contradicts a step's state, action, event or outcome. A fact present at another line than cited is a correction noted in the step, not a refutation. A part is Confirmed when every step is confirmed or corrected, else Unverifiable. `python3 scripts/check_artifacts.py verify <file>` checks the shape. Verifiers run nothing but that script.

The synthesizer then adds a **Verified:** line to each handoff's Readiness slot with the three verdicts and the refuted or unverifiable items. Only the Outcome verdict decides the handoff's place: Refuted moves it to Lower rows with the refutation, and its ledger row stays with Result `refuted at verify`; Confirmed or Unverifiable keeps it, with unverifiable steps named. A refuted Remedy routine or Verification seam is corrected inside the handoff: the remedy names another routine or states the premise, the check that passes today is replaced or dropped. Run `python3 scripts/check_artifacts.py synthesis <file> --model <model.md> --verified` before returning.

## Authorized implementation

Compare alone does not authorize project edits. When the user also asks for fixes, take the handoff into the project's coding workflow: check the current baseline, make recoverable scoped changes, run the discriminating checks, report what passed. Preserve open evidence gaps rather than closing every row speculatively. Do not repeat the compare, or request approval already supplied, merely to start implementation.
